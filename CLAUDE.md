# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A stdio MCP server (ModelContextProtocol 2.2.0, .NET 10) that decompiles .NET assemblies to C# with the ILSpy engine (`ICSharpCode.Decompiler`). Each DLL is exported **to disk** as an ILSpy project (one `.cs` per top-level type under a namespace folder, plus a `.csproj`) into an output tree mirroring the scan directory; tools return paths, summaries and short line snippets, never whole files. It exposes five tools over a recursively scanned DLL directory: `list_assemblies`, `decompile_assembly`, `decompile_type`, `decompile_all`, `search_code`. With `--EnableLanguageServer true` it adds six semantic tools backed by a Roslyn language server it hosts: `find_symbol`, `get_document_symbols`, `go_to_definition`, `find_references`, `find_implementations`, `hover`. One server project at the root (no `src/` folder; the language-server code is in `LanguageServer/`), one xUnit project in `tests/DecompilerMCPServer.Tests`, solution file `DecompilerMCPServer.slnx`.

## Commands

```bash
dotnet build -c Release                 # -> bin/Release/net10.0/DecompilerMCPServer
dotnet publish -c Release -r osx-arm64  # self-contained single file (also osx-x64, win-x64, win-arm64)
dotnet test tests/DecompilerMCPServer.Tests
```

The server csproj sits at the repo root, so its default globs would pick up the test sources; `<DefaultItemExcludes>` drops `tests/**`. Keep that when adding files.

Run the built binary directly, never via `dotnet run` (MSBuild output on stdout corrupts the JSON-RPC stream):

```bash
./bin/Debug/net10.0/DecompilerMCPServer --ScanDirectory /path/to/dlls [--OutputDirectory /path/to/sources]
```

The unit tests cover the language-server pure logic (symbol name parsing, workspace generation, discovery, installer, LSP JSON). There is no CI on push/PR. Smoke testing:

- Bare run with no args must exit 1 and print a message containing `ScanDirectory` to stderr. Both install scripts (`scripts/install.sh`, `scripts/install.ps1`) rely on this as their post-install check. Do not change that exit code or message substring.
- End-to-end: pipe JSON-RPC lines (`initialize` → `notifications/initialized` → `tools/call`) into the binary. Keep stdin open until the response is read (e.g. `( printf '...'; sleep 1 ) | ./bin/...`), otherwise the server shuts down before flushing. The project's own `bin/Debug/net10.0` is a convenient corpus (contains a duplicated simple name for ambiguity tests). Always pass `--OutputDirectory` pointing at a scratch folder when testing, or the default under `~/Library/Application Support/DecompilerMCPServer/sources/` fills up. A large DLL like `ICSharpCode.Decompiler.dll` takes ~40s to export the first time (874 files); the on-disk manifest makes repeats instant, even across restarts. Staleness can be forced with `touch` on the DLL or by editing the `Mvid` in the project folder's `.decompiled.json`. With the watcher on (the default), the server starts exporting the whole scan directory at startup; pass `--WatchScanDirectory false` to test the on-demand paths in isolation.
- The scan and output directories must not be the same or nested; the server exits 1 for that too, but only **after** the `ScanDirectory` check, so the bare-run contract above is unaffected. The same holds for the language-server settings (`EnableLanguageServer` non-boolean, missing `LanguageServerPath`/`DotnetPath` file, bad `LanguageServerLoadTimeoutSeconds`).
- Language server end-to-end: add `--EnableLanguageServer true`, copy a few related DLLs (e.g. `ModelContextProtocol*.dll`, `Microsoft.Extensions.Options.dll`, `Microsoft.Extensions.DependencyInjection.Abstractions.dll`, `Microsoft.Extensions.Primitives.dll` from `bin/Debug/net10.0`) into a scratch scan folder so the load stays fast, then call e.g. `go_to_definition` with `{"file":"ModelContextProtocol.dll/ModelContextProtocol/McpServerOptionsSetup.cs","line":9,"symbol":"McpServerOptions"}`; it must land in `ModelContextProtocol.Core.dll/...` (a cross-assembly ProjectReference). The first LSP call takes 10–40 s (exports + server load), later ones well under a second. Force the download path with `--LanguageServerVersion 5.11.0` (skips editor discovery); force a specific server with `--LanguageServerPath`. Kill the `dotnet ...LanguageServer.dll ... --clientProcessId=<server pid>` child to test the crash restart. stderr logs which server was chosen (`Using Roslyn language server ... from ...`).
- Register with a real client: `claude mcp add decompiler -- <abs path>/DecompilerMCPServer --ScanDirectory <dir>`, then `/mcp`.

Release: `git tag v0.1.0 && git push origin v0.1.0`. Tags containing `-` are published as prereleases. The workflow cross-compiles all four RIDs on Ubuntu and passes the tag as `-p:Version`, which overrides `<Version>` in the csproj; keep the two in sync by hand.

## Architecture

`Program.cs` validates `ScanDirectory` (from `--ScanDirectory` arg or the bare `ScanDirectory` env var, via the standard config stack) **before** starting the transport, then resolves `OutputDirectory` (same stack; default `<LocalApplicationData>/DecompilerMCPServer/sources/<leaf>-<8 hex of sha256(lowercased scan path)>`), rejects same/nested directories, creates it, parses `WatchScanDirectory` (default `true`; a non-boolean value exits 1) and `EnableLanguageServer` (default `false`, same rule) plus, when enabled, `LanguageServerPath`, `LanguageServerVersion`, `DotnetPath`, `LanguageServerLoadTimeoutSeconds` (default 300), registers the singletons, `ScanDirectoryMonitor` as a hosted service when watching is on, and `WithTools<DecompilerTools>()`; the language-server services and `WithTools<LanguageServerTools>()` are registered only when enabled, so the tool list is unchanged otherwise. Console logging is routed entirely to stderr (`LogToStandardErrorThreshold = LogLevel.Trace`).

- `DecompilerTools.cs` — the tool surface. `[McpServerToolType]` class with a primary constructor injecting the three services below. `decompile_all` takes an `IProgress<ProgressNotificationValue>` parameter that the SDK binds automatically (no-op when the client sent no progress token); it is not part of the tool schema.
- `AssemblyDiscoveryService.cs` — recursive `*.dll` scan (fresh walk every call, nothing cached) and identifier resolution: exact relative path first, then simple name (`.dll` appended if missing). Multiple matches return an "Ambiguous" error rather than picking one. Also defines the `ScanOptions` and `ExportOptions` records.
- `ProjectExportCache.cs` — ensures a DLL's project exists at `<OutputDirectory>/<scan-relative path incl. .dll>/` and returns a `ProjectExport` record. In memory: `ConcurrentDictionary<string, Entry>` keyed by full path (`StringComparer.Ordinal` on purpose) with a `Lazy<ProjectExport>` (`ExecutionAndPublication`, exception cached until the DLL's size/timestamp stamp changes, only cancellation evicts). On disk: a `.decompiled.json` manifest in the project folder (assembly path, mtime ticks, length, MVID, ILSpy version, format version, counts); when all match, the export is reused without touching ILSpy. Otherwise it takes a cross-process lock (`<projectDir>.lock`, `FileShare.None`, 250 ms retry), deletes stale `.tmp-*` siblings, exports into `<projectDir>.tmp-<pid>`, writes the manifest last, deletes the old folder and `Directory.Move`s the temp into place. `DeleteOwnedDirectory` refuses to delete anything not under `OutputDirectory` and not named `*.dll` / `*.dll.tmp-*`; keep that guard.
- `DecompilerService.cs` — ILSpy wrapper. `ExportProject` builds a `PEFile` + `UniversalAssemblyResolver` (same construction `CSharpDecompiler(string, settings)` uses) and a **fresh** `WholeProjectDecompiler` per call (it holds per-export state). `ThrowOnAssemblyResolveErrors = false` is deliberate: user folders have no guaranteed reference closure, so unresolved types in output are expected. Settings are otherwise ILSpy defaults, so `UseNestedDirectoriesForNamespaces` is off and a namespace is one folder. `GetTypeFileRelativePath` reproduces ILSpy's file naming with its own public `CleanUpDirectoryName`/`CleanUpFileName` helpers (generic arity dropped, nested types -> outer file); change the settings and this mapping must follow. `ContainsType` is a metadata-only probe (`System.Reflection.Metadata`) that matches top-level type names only. `ReadMvid` is the metadata-only module version id used by the manifest.
- `ScanDirectoryMonitor.cs` — `BackgroundService` (on unless `--WatchScanDirectory false`). `ExecuteAsync` hands off to `Task.Run` so startup is never blocked. Starts a recursive, unfiltered `FileSystemWatcher` first, then runs a *reconcile*: `GetExport` for every DLL (skipping ones with a pending debounced event) and `RemoveExport` for every exported project (`ProjectExportCache.FindExportedAssemblies`) whose DLL no longer exists. Created/Changed `*.dll` → per-path export after a 2 s debounce; directory Created, any Deleted/Renamed, and watcher `Error` → debounced full reconcile (deleting a folder raises one event). One worker thread, so exports are serial; `IOException`/`UnauthorizedAccessException` retries with backoff (5 attempts); everything else is logged and skipped; the loop never throws out. Tools that need a DLL being exported join the same `Lazy` in the cache and wait. `GetExport` reports `Reused = true` to any caller that didn't create the entry, so in-memory hits and exports made by the monitor show as reused.

Which tools export: `decompile_assembly`, `decompile_type` (once the owning assembly is known), `search_code` (every target, so the first unfiltered search pays a full export of every DLL) and `decompile_all`. `decompile_type` without `assembly` first re-reads metadata of every DLL on each call to find the owner. ILSpy skips compiler-generated/hidden types (`<Module>` etc.), so `decompile_type` checks `File.Exists`, then tries a `<name>.*.cs` companion (XAML/resx-backed types), then returns an error. The first language-server tool call exports every DLL too (the workspace needs all of them).

`ProjectExportCache` raises `ExportsChanged(relativePath)` after a fresh export (only to the caller that created the entry, outside the lock) and after `RemoveExport` deleted a folder; handler exceptions are logged, never propagated. `FindExportedAssemblies` skips the root `.lsp` folder. `FileLock.cs` is the shared cross-process lock-file helper (export cache and installer).

### Language server (`LanguageServer/`, opt-in)

Modeled on Serena's `csharp_language_server.py`. Flow on the first LSP tool call, single-flight under a semaphore in `RoslynLanguageServerHost`:

1. `DotnetLocator` — first of `--DotnetPath`, `DOTNET_ROOT_<ARCH>`, `DOTNET_ROOT`, `PATH`, default install dirs, `~/.dotnet` whose `--list-runtimes` has `Microsoft.NETCore.App` 10+; prefers one that also has a 10+ SDK (MSBuild loads the projects), otherwise warns. Explicit `--DotnetPath` never falls back.
2. Export every scanned DLL (retrying transient IO errors) and `WorkspaceGenerator.Generate()`, which writes three files at the output root, only when their content changed: `DecompiledWorkspace.slnx` (all exports); `Directory.Build.props` redirecting `BaseIntermediateOutputPath`/`BaseOutputPath` to `.lsp/build/<relative>/` (the server restores on its own, and `obj/` inside an export would leak generated `.cs` into `search_code`); `Directory.Build.targets` with one `ItemGroup Condition="'$(MSBuildProjectFullPath)' == '...'"` per project doing `Reference Remove` + `ProjectReference` for every `HintPath` that resolves to another export's DLL, when NuGet.Frameworks says the TFMs are compatible, dropping edges that would close a cycle. ILSpy's `.csproj` files are never modified, so `FormatVersion` is unaffected; a sibling csproj was rejected because two projects in one folder compile the same files.
3. `RoslynServerLocator.FindCompatible` — `--LanguageServerPath` (used as is, warning if the check fails), then our cache `<LocalAppData>/DecompilerMCPServer/roslyn-ls/<version>/<rid>/` newest first, then `ms-dotnettools.csharp-<ver>[-<vscode platform>]/.roslyn/` under `~/.vscode`, `-insiders`, `-server`, `-oss`, `~/.cursor`, `~/.windsurf` (+ `-server`), newest first, then the `roslyn-language-server` dotnet tool store. `--LanguageServerVersion` restricts to the cache (no editor builds). `CheckCompatibility` is process-free: DLL + runtimeconfig present, every framework satisfied under its `rollForward`, assembly version >= `MinimumVersion` (5.0). Candidates that fail `initialize` are blacklisted for the process lifetime and the next one is tried; the download is the last resort.
4. `RoslynServerInstaller` (fallback) — `https://api.nuget.org/v3-flatcontainer/roslyn-language-server.<rid>/<ver>/...nupkg`, redirects followed by hand against a nuget.org host allowlist, SHA256 checked against `DefaultSha256` for `DefaultVersion` (other versions are unverified with a warning), `tools/<tfm>/<rid>/**` extracted with a zip-slip guard into `<dir>.tmp-<pid>` and moved into place (retrying: antivirus holds fresh DLLs on Windows), under a `<dir>.lock` file lock. **Bumping the pinned version means updating `DefaultVersion` and all six hashes together** (download each `roslyn-language-server.<rid>` nupkg and `Get-FileHash`/`shasum -a 256`).
5. `LspClient` — `dotnet <dll> --stdio --logLevel=Information --extensionLogDirectory=<roslyn-ls>/logs --clientProcessId=<our pid>` (the server exits if we die), `DOTNET_ROOT`/`PATH` pointed at the chosen dotnet. StreamJsonRpc `HeaderDelimitedMessageHandler` + `SystemTextJsonFormatter`; requests take anonymous objects and return `JsonElement` (2 min timeout), DTOs in `LspTypes.cs`. Server→client handlers: `window/logMessage` (load tracking + logging), `workspace/configuration` (nulls), `workspace/_roslyn_projectNeedsRestore` (no-op: the server restores itself), and no-op stubs for progress/registration/diagnostics. `initialize` must report definition/references/documentSymbol/hover/implementation/workspaceSymbol providers.
6. `solution/open`, then readiness: Roslyn signals nothing reliable, so `WaitUntilLoadedAsync` watches the log: a newer `Completed (re)load of` line (wording varies by version: "N project(s)" / "all projects") plus 2 s quiet with no `Running dotnet restore` in flight, **or** 15 s with no project-system activity since the open (the server's own file watcher may already have reloaded, and then no new completion is logged). Times out after `LoadTimeout`, after which requests proceed against whatever is loaded. A load generally logs a completion before *and* after the automatic restore.

After start: `ExportsChanged` arms a 2 s debounced reload (changes older than the last generated workspace are ignored), which regenerates the workspace, `didClose`s open documents (their buffers would shadow re-exported files), clears the documentSymbol cache and re-sends `solution/open`. A dead process is restarted on the next call, at most 3 crashes per 5 minutes. Documents get `didOpen` before position requests (LRU of 32). `SymbolResolver` turns names into positions: `workspace/symbol` (fuzzy; its container is `"project X (tfm)"`, not the namespace) narrows candidate files by simple name, then each file's `documentSymbol` tree is flattened into qualified entries (namespace names split on `.`) and matched by suffix on name, per-segment generic arity, and normalized parameter list; if nothing matches it resolves the container type first and searches its file (`workspace/symbol` is capped). Roslyn display names are `Add(int, int) : int`, `Name : string`, `Widget<T>`; **constructors are kind 6 (method) named after the type**, so `..ctor` queries match kind 6/9 and `find_symbol` has no constructor filter. `LanguageServerTools` prefers a unique type over its same-named constructors, reports ambiguity as an `Error:` list (max 20), and reports locations outside the output directory (Roslyn's `MetadataAsSource` temp files for framework/unresolved types) as `(external) [Assembly] <line>`.

## Conventions

- **stdout is sacred.** Never `Console.WriteLine` to stdout; logs go to stderr, startup errors use `Console.Error.WriteLine`.
- Tools return `string`. User-facing failures are returned as text starting with `"Error: "` plus a remediation hint, not thrown. `OperationCanceledException` is always re-caught and rethrown before the generic `catch (Exception)`.
- Per-item resilience: in multi-assembly operations a bad DLL is skipped (`(skipped: ...)` in `search_code`, silently in the `decompile_type` probe); the server never dies from bad input.
- Adding a tool: add a method to `DecompilerTools` (or `LanguageServerTools` for LSP-backed ones) with `[McpServerTool(Name = "snake_case")]`, a `[Description]` on the method and on every parameter, and `CancellationToken cancellationToken = default` last. No registration change needed. A new tool *class* needs its own `.WithTools<T>()` in `Program.cs`.
- `search_code` clamps `contextLines` to 0–10 and `maxResults` to 1–500, and uses a 2-second regex match timeout; it reads the exported `*.cs` files (sorted ordinal) and labels each group with the absolute file path. `decompile_assembly` lists at most 50 namespace folders. LSP tools: `find_symbol` `maxResults` 1–200 (default 50); `find_references`/`find_implementations` `maxResults` 1–500 (default 100); `contextLines` 0–10 (default 2 for `go_to_definition`, 0 otherwise); `get_document_symbols` stops at 2000 entries; lines/columns are 1-based at the tool boundary, 0-based on the wire; `file` arguments must resolve to an existing `.cs` under `OutputDirectory`. The README tool tables mirror these numbers; update both together.
- Tool annotations: `list_assemblies` is `ReadOnly`; the exporting tools and all LSP tools are `Idempotent = true, Destructive = false` (the attribute defaults `Destructive` to true).
- LSP tools wrap everything in `RunAsync`: `LanguageServerUnavailableException` -> `Error: language server unavailable: ...` (its message must say how to fix it), other failures -> `Error: language server request failed: ...`.
- The manifest `FormatVersion` constant in `ProjectExportCache` must be bumped whenever the on-disk layout or naming changes, so old exports are regenerated.
- Nullable and implicit usings are enabled.

## Release artifacts and installers

- Artifact name `DecompilerMCPServer-v{version}-{rid}.{tar.gz|zip}` is hardcoded in three places that must move together: `.github/workflows/release.yml`, `scripts/install.sh`, `scripts/install.ps1`. `SHA256SUMS` holds bare filenames; `install.sh` greps one line and pipes it to `shasum -a 256 -c -` (macOS has no `sha256sum`).
- `install.sh` is macOS only and refuses to run elsewhere; there is no Linux artifact. Adding one means touching the RID loop in the workflow.
- Binaries are unsigned. `install.sh` strips quarantine and applies an ad-hoc `codesign`; `install.ps1` runs `Unblock-File`. `install.ps1` is written for Windows PowerShell 5.1 compatibility.
- Windows is cross-compiled from Ubuntu and has no CI; treat it as untested end-to-end. The install one-liners require the repo to be public.
- Both installers accept a version via positional arg / `-Version`, then `DECOMPILER_MCP_VERSION`, else latest. `DECOMPILER_MCP_BASE_URL` points them at a local server (a `file://` or `python -m http.server` base) for testing.
